## 2. 확인된 구조

### 2.1 압축 (LZ) — 확인

- 형식: `[풀린 크기 3바이트 LE][창 종류 1바이트]` + Okumura LZSS (플래그 바이트 LSB부터, 1=리터럴, 0=참조 2바이트 `pos = b0 | (b1 & 0xF0) << 4`, `len = (b1 & 0x0F) + 3`, 링 시작 = N−18, 링 초기값 0).
- 창 종류: `0` → N=4096, `1` → N=1024.
  - 근거: `TITLEBG.PXT`(종류 1)를 N=1024로 풀어 상하 반전하면 타이틀 화면 세이브 스테이트의 VDP2 VRAM 비트맵과 **640×240 전 화소 일치**(N=4096이면 37%만 일치). `.SA` 7개(종류 0)는 N=4096으로 풀었을 때 깨끗한 글자 그림이 나오고 N=1024면 깨짐.
  - 게임 해제 루틴 코드는 아직 직접 읽지 않음. 압축기를 만들 때 해제 루틴 확인 또는 실기 대조로 호환성을 확인한다(R-3).
- 게임 해제 루틴 확인 (SH-2 역어셈블):
  - 종류 0: `0.BIN` `0x0601068C` — 4바이트 전체를 크기로 읽음, 링 `[0, 0xFEE)`만 0으로 지움(스택 위 링, 끝 18바이트는 이전 값), 바이트마다 출력 수를 세어 정확히 멈춤.
  - 종류 1: `MAIN.BIN` 파일 오프셋 `0x1FC94`, `0x1FD74` — 3바이트 크기, 정적 링 `0x0607C420`(1024바이트) `[0, 0x3EE)`만 지움, 토큰 단위로 멈춤(마지막 참조가 크기를 넘으면 넘쳐 씀).
  - 제품 압축기 `tools/steamhearts/lzss.py`는 지우지 않은 꼬리를 읽지 않고, 마지막 토큰이 크기에 정확히 끝나게 만든다.

### 2.4 일본어 글꼴이 없음

- 디스크의 모든 비압축 파일(실행 파일 `0.BIN`·`MAIN.BIN`·`CPKPLAY.BIN`·`FILEX.BIN` 포함)에서 Shift-JIS 문자열이 나오지 않음(잡음 일치만).
- 압축 그림을 모두 풀어 봄: `.PXT` 46개, `.SPT` 48개 전 프레임, `.SA` 7개. 일본어 글꼴로 쓸 만한 글자 묶음은 없고, 일본어는 아래 3절의 완성 그림 글자뿐.
- 결론: 이 게임에는 **문자 코드로 찍는 일본어 문장이 없다**. 스테이지 대화·비주얼 장면(그림 `VIS*_?S.PXT` + 음성 `VIS*?.AIF`)은 자막 없이 음성으로만 나온다고 판단. 비주얼 장면 실제 화면은 아직 못 봄(R-4).

### 3.1 백업 RAM 안내 그림의 소비 경로 (확인)

- `0.BIN`이 소문자 이름(`"broken.sa"` 등, `0x06010A38`–`0x060111C0`)으로 GFS에서 읽어 `0x060D0000`에 올리고, 해제 함수 `0x0601068C`로 `0x060DC000`에 풀어, 복사 함수 `0x060107C8`로 VDP2 비트맵(`0x25E00000`, 줄 간격 512화소)에 옮긴다.
  - `siyo.sa`: 320×224 전체. `ram.sa`: 200×16 한 줄을 선택에 따라 원본 0행 또는 16행(`+0x1900`)에서 `0x25E1B87C`로.
  - `readnow.sa`: 320폭 줄을 장치에 따라 0행 또는 16행에서, 「OK!」는 32행에서.
  - `yesno.sa`: 96×16 한 줄을 선택에 따라 안내 그림 위 (108,182)에 겹쳐 그림.
- 부팅 시 장치별 상태 바이트 두 개(본체, 카트리지)가 모두 `-4`이면 데이터 선택(`0x06010D5C`), `-4`이면 읽기(`0x060111CC`, readnow), `-3`이면 `0x06010F48`, 그 밖은 `0x06010A50`. 상태 값의 정확한 의미는 미확인.

## 4. 개입 방식

- 모두 **데이터 교체**. 코드 수정·글꼴·문자 코드 작업은 필요 없음.
- `.SA`, `.SPT`: 새 그림 → (SPT는 조각 나누기) → LZ 다시 압축. 파일이 원래 크기보다 커지면 ISO 안 위치 이동 또는 로더 확인이 필요(R-1).
- 타이틀 로고는 16색 1팔레트(4bpp)로 줄여야 한다. 제공된 `title_ko.png`(2172×724, 투명 배경)는 흰색 입체 글자 + 빨간 부제라 16색 안에서 표현 가능해 보이나, 그라데이션이 줄어든다.
- 타이틀 화면은 640×240 고해상도(화소 세로가 2배 길게 보임) → 로고 그림은 세로를 절반으로 줄여 넣어야 원래 비율로 보인다.

### 4.2 타이틀 로고와 스태프 롤 (2026-10-02)

- **SPT 구조 확인:** 첫 u16은 가장 큰 프레임 블록의 풀린 크기(작업 버퍼)와 5개 파일에서 정확히 같음. 로더는 프레임 블록을 순서대로 VDP1 VRAM에 이어서 푼다(타이틀: `0x080C0`부터). 타이틀 로고 8프레임 모두 화면 위치 = (320,112) + 프레임 x,y + 조각 x,y. 제품 SPT 작성기는 원본 블록을 넣으면 헤더·조각표·레코드 배치를 원본과 똑같이 재현한다.
- **타이틀 로고 (`SHLOGO.SPT`):** `title_ko.png`를 506×88(640×240 화면 기준, 원래 로고의 세로 범위 y 72..160)로 줄이고 14색+투명으로 바꿔 8프레임(굵은 글자 세로 띠 7개 + 빨간 부제 1개)에 나눔. 6,068바이트로 원래 3섹터 안, VRAM 17,888바이트(원래 22,400 이하), 가장 큰 블록도 작업 버퍼(4,928) 이하. 15색이면 6,151바이트로 3섹터를 넘어서 14색으로 정함.
  - 실행 확인: 타이틀 화면에 한글 로고 표시, VDP1 VRAM `0x080C0`의 텍스처가 빌드 결과와 바이트 단위로 같고 61개 조각이 모두 그려짐. 엔딩 뒤 타이틀에서도 같은 로고.
- **스태프 롤 (`SR.SPT`):** 36프레임 = 18블록 × (화면 중앙 기준 왼쪽 절반, 오른쪽 절반). 글자는 640×240 화면에 맞춰 정사각형으로 그린 뒤 세로를 절반으로 줄임(줄 간격 12줄). 4단계 회색 중 가장 어두운 단계를 빼서 19,130바이트로 원래 10섹터(20,480) 안에 넣음(4단계 모두 쓰면 22,623바이트). 마지막 블록의 戯画 로고는 원본 화소 유지.
  - 실행 확인: 아래 시험 디스크로 엔딩을 재생, 엔딩 그림 위로 한글 스태프 롤이 흐르고 마지막 「기획 / 개발」+로고까지 표시. 첫 시험에서 원본 블록 기준 행을 프레임 원점으로 잡아 8줄 어긋나 일본어 잔상이 남던 버그를 찾아 고침(테스트 추가).
- **엔딩·비주얼 장면 도달 (상태 개입, 제품 아님):** `MAIN.BIN`(역시 `0x06010000`에 적재)의 메인 루프 `0x060339A8`: 모드 변수 `0x0605D716`(0 타이틀, 1 스테이지, 2 리셋, 3 장면), 장면 번호 = 스테이지 카운터 `0x0605D710`, 장면 함수 `0x06035364`(0–5, 8 = 비주얼 장면 1–7, 9 = 엔딩 `0x06034E30`). 시험 디스크(`work/testdisc.py`)는 한글 빌드에서 `MAIN.BIN` 두 곳(`0x239B4` 처음 모드 0→3, `0x23A56` 장면 번호 고정)만 바꿔 부팅 직후 장면을 재생한다. 정상 플레이로 엔딩에 간 것은 아님.
- **현재 제품 빌드:** 9개 파일, 65섹터 변경, 출력 SHA-1 `a8648a630583a2aef36c87c737127ee3e506d8fd` (타이틀·엔딩 실행 확인은 이 출력으로 함). 코드 리뷰 반영(압축 스트림을 임의의 링 꼬리 값으로 두 번 풀어 확인, 같은 섹터 이중 쓰기 거부, 번역 없는 배치 칸 거부, 잘린 BIN 감지) 뒤에도 출력이 같음.
